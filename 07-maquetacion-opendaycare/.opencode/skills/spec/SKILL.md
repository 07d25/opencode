# /spec — Simple, production-safe spec flow

---

`/spec` is one skill with three explicit modes. Each feature stays together:

```text
specs/NNN-slug/
├── spec.md          # WHAT & WHY
├── plan.md          # HOW
├── tasks.md         # EXECUTION
└── retrospective.md # generated by spec-verifier after verification
```

## Commands

| Command | Creates | Purpose |
| --- | --- | --- |
| `/spec <idea>` or `/spec new <idea>` | `spec.md` | Define what is built, why, scope, production security, failures, and acceptance criteria. |
| `/spec plan <NNN-slug>` | `plan.md` | Define the technical approach after inspecting the repository. |
| `/spec tasks <NNN-slug>` | `tasks.md` | Define small ordered tasks, evidence, dependencies, and traceability. |

The user must manually change each document to `Approved` before its successor can be created. The next stages are `/spec-impl NNN-slug`, then the `spec-verifier` agent.

Replies and artifact bodies use the user's language. IDs and code remain English.

## Mode: new (default)

Use this mode when `$ARGUMENTS` does not begin with `plan` or `tasks`.

1. Read `AGENTS.md`, then inspect existing `specs/` folders. If prior specs exist, read the two most recent to follow their language and conventions.
2. If no idea was provided, ask for a one-sentence description.
3. Ask questions in blocks of 3–5 until there are no material assumptions about: scope, data, integration, UX/states, persistence, authorization, sensitive data/PII, validation, secrets, failure/degradation, rollout/rollback, risks, and acceptance criteria.
4. For a production-affecting change, explicitly close authorization, validation, PII, secrets, rate limits/audit trail, failure behavior, rollback, and observability requirements. Record `not applicable` with a reason instead of silently omitting a topic.
5. If the feature is too big (more than three areas or several independent decisions), propose splitting it.
6. Read `references/spec-template.md`, create `specs/NNN-slug/spec.md`, and seed `specs/.spec-config.yml` when missing:

   ```yaml
   # spec workflow configuration
   AutoCreateBranch: true
   ```

   Use the next available three-digit number. Set status to `Draft`; never approve it automatically.
7. Confirm the path and tell the user: review it, manually set it to `Approved`, then run `/spec plan NNN-slug`. Stop.

## Mode: plan

Use this mode for `/spec plan <NNN-slug>`.

1. Resolve the feature folder from its full name, number, or slug. Read `spec.md`.
2. Continue only if `spec.md` means **Approved**. Otherwise stop and tell the user to finish/review it first.
3. If open questions in the spec block technical design, ask only those questions and wait.
4. Inspect the actual repository before proposing anything: architecture, stack/versions, project rules, reusable modules, persistence/migrations, auth/authorization, security posture, test setup, dependencies, configuration, and deployment constraints. Record paths/commands as evidence. Never invent findings.
5. Read `references/plan-template.md` and write `specs/NNN-slug/plan.md`. Keep the fixed sections Migration, Rollback, and Observability; use `*(not applicable: reason)*` when appropriate.
6. Set status to `Draft`. Confirm the path and tell the user: review it, manually set it to `Approved`, then run `/spec tasks NNN-slug`. Stop.

## Mode: tasks

Use this mode for `/spec tasks <NNN-slug>`.

1. Resolve the feature folder. Read `spec.md` and `plan.md`.
2. Continue only if both mean **Approved**. If either is missing or not approved, stop and point to the required prior command.
3. Read `references/tasks-template.md` and write `specs/NNN-slug/tasks.md` from the plan's implementation and test strategies.
4. Tasks use `TASK-nnn` and states `TODO`, `IN_PROGRESS`, `BLOCKED`, `DONE`. Each task has: one result, dependencies, files/modules, steps, tests, a verifiable completion condition, and required evidence.
5. Include a traceability matrix `Requirement → AC → Task`. Every acceptance criterion needs at least one task; an uncovered row blocks completion.
6. The task document itself has no approval state. It is ready only when the spec and plan remain Approved and no traceability row is `Not covered`.
7. Confirm the path and tell the user: run `/spec-impl NNN-slug`. Stop.

## Non-negotiable rules

- Do not write product code in any mode.
- Keep requirements in `spec.md`, technical choices in `plan.md`, and execution breakdown in `tasks.md`; do not duplicate them.
- Never invent repository findings, test results, or production evidence.
- Acceptance criteria must be binary and verifiable. No "works well" or "good UX".
- Never silently expand scope. Update the spec first.
- Do not create commits, push, or deploy.
